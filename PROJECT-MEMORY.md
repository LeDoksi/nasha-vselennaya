**Что поменялось 11.08.2026 (в этом чате):**

- **`npm run check` падал** — `tests/uni-photo-sync.js` дёргал `makeYdStorage`,
  функцию из уже удалённой Яндекс.Диск-реализации (осталась после миграции на

- **Архитектура фото-облака приведена в порядок.** Раньше в коде было три
  параллельных, местами мертвых пути: (1) `makeRtdbPhotoStorage()` — реально
  работавший путь, фото текстом в Firebase RTDB (не рассчитан на блобы, лимит
  free-плана ~1 ГБ); (2) `makeCloudStorage()` — S3-подпись (AWS SigV4) для
  Yandex Object Storage с ключом/секретом — определена, но **никогда не
  вызывалась**; (3) `YANDEX_S3_KEY`/`YANDEX_S3_SECRET`, которые
  `deploy-pages.yml` вписывал бы прямым текстом в публичный `index.html` при
  деплое — секрет с правом записи/удаления в открытом виде на публичной
  странице. Решение (по прямому запросу пользователя — «хочу, чтобы всё
  хранилось на Яндексе», проверено против доков yandex.cloud/docs/storage):
  фото (orig+full+thumb) теперь **всегда** идут через `makeCloudStorage()` в
  Yandex Object Storage, но **без ключей на клиенте** — бакет настроен
  публичной bucket policy, ограниченной префиксом `photos/*` (см. README,
  раздел «B2. Yandex Object Storage»). `makeRtdbPhotoStorage()` удалена как
  мёртвый код, Firebase используется только для `vaults/shared` (сам
  крошечный зашифрованный сейф, не фото). Confidentiality держится не на
  секретности доступа, а на том, что в бакете лежит только AES-GCM шифртекст —
  тот же принцип, что уже был принят для Firebase RTDB (`auth != null`,
  открыт любому анониму).
- **Побочный баг найден и исправлен:** `makeCloudStorage().ref(path).listAll()`
  строил префикс листинга как `'photos/' + encodeURIComponent('photos/orig')`
  — задвоенный `photos/` и неверно закодированный `/`. Из-за этого
  `listCloudPhotos()` всегда видел бы пустое облако, и скачивание фото на
  втором устройстве никогда бы не сработало. Было не покрыто тестами (старый
  тест гонял другой, Яндекс.Диск-адаптер). Тест на `makeCloudStorage()`
  добавлен, баг закрыт.
- **`secrets.js`** (реальные S3-ключи, больше не нужны) добавлен в
  `.gitignore` и удалён; GitHub Actions secrets `YANDEX_S3_KEY`/
  `YANDEX_S3_SECRET` удалены из репозитория — архитектура их не использует.
- **Известный исторический факт:** старый Яндекс.Диск OAuth-токен (scope
  `cloud_api:disk.app_folder`) какое-то время лежал в открытом виде в
  `app.js` на публичном GitHub Pages (до миграции на S3-подход). Пользователь
  в курсе и решил не отзывать его специально («никто не видел») — просто
  вычищать секреты из будущих коммитов. Токен из текущего кода полностью
  убран, но остаётся в старых git-коммитах публичного репозитория.
- **ПОПРАВКА (тем же вечером 11.08.2026, после живого теста с фото):** гипотеза
  выше — «бакет полностью публичен через bucket policy, ключи вообще не
  нужны» — оказалась **наполовину неверна**. Проверено вживую (curl напрямую
  в реальный бакет + скриншоты консоли пользователя): анонимное **чтение**
  (`GetObject`/`ListBucket`) действительно работает через bucket policy — но
  анонимная **запись** (`PutObject`/`DeleteObject`) у Yandex Object Storage
  **не работает никогда**, даже если политика формально её разрешает (сервер
  стабильно отвечает `403 AccessDenied`, задержки/пропагации ни при чём —
  проверено повторными запросами). В официальной документации нет ни одного
  примера, где `PutObject`/`DeleteObject` выдаются `Principal: "*"` — судя по
  всему, это намеренное ограничение платформы, а не баг конфигурации.
  Побочно найдено и исправлено ещё две вещи по пути: (1) `s3:ListBucket` в
  политике требует **ресурс-бакет** (`arn:...:::bucket`), не
  `bucket/photos/*` — иначе тоже 403; (2) после сохранения ЛЮБОЙ кастомной
  bucket policy консоль сама теряет доступ к разделам «Объекты»/«CORS»
  этого бакета, пока не добавлено служебное правило `AllowAWSServices` с
  условием `aws:PrincipalIsAWSService: true` (кнопка «Добавить правило для
  доступа из консоли» в редакторе политики) — задокументированная, но
  контринтуитивная особенность.
  **Решение (выбрано пользователем из 3 вариантов):** добавлена Cloud
  Function `functions/photo-sign/index.js` — маленький сервер, который
  держит статический S3-ключ (`YC_S3_KEY`/`YC_S3_SECRET`, только в
  переменных окружения функции, никогда не в клиентском коде) и по запросу
  отдаёт **presigned URL** (AWS SigV4, query-подпись, время жизни 60с) на
  `PUT`/`DELETE` конкретного `photos/{part}/{id}`. Дальше браузер сам делает
  запрос по этой ссылке напрямую в бакет — тело файла через функцию не идёт
  (это заодно снимает вопрос про лимит размера запроса функции, 3.5 МБ,
  который иначе резал бы крупные оригиналы фото). `makeCloudStorage()` в
  `src/95-sync.js`: `getBlob()`/`listAll()` — как раньше, анонимно и напрямую;
  `put()`/`delete()` — через `presignedFetch()` → сначала `GET` на
  `YANDEX_CLOUD_CONFIG.signFnUrl`, потом сам запрос по полученной ссылке.
  Инструкция по деплою функции — README, раздел «B3. Cloud Function
  photo-sign». Тесты (`tests/uni-photo-sync.js`) обновлены: мок `fetch` умеет
  отвечать и на вызов функции подписи (`signCalls`), и на сам PUT/DELETE по
  «подписанной» ссылке; добавлена проверка, что запись реально идёт через
  функцию, а не голым PUT в бакет.

`cloud_api:disk.app_folder` видит **только папку приложения** (в вебе —

корня диска (`/photos/...`). Итог: все запросы к cloud-api.yandex.net падали
с **403 Forbidden**, папка приложения на Диске существовала, но оставалась

**Восстановление облачных данных при входе (10.08.2026).** Найдена и исправлена
причина «В облаке сейф, зашифрованный другим паролем» на свежем браузере: если
на устройстве оставался ЛОКАЛЬНЫЙ сейф, `tryUnlock` проверял пароль только по
нему — облачный сейф (даже с правильным паролем) не пробовался, и данные из
облака не приходили. Теперь:
- `tryUnwrapKey(who, pass, vault)` — проверка пароля без побочных эффектов;
- `tryUnlock` пробует пароль СРАЗУ по локальному и облачному сейфу
  (`pendingCloudVault`, ищется в `initAuth` всегда, не только без локального):
  - локальный не открылся, облачный открылся → вход облачным (новый браузер);
  - открылись оба, но это РАЗНЫЕ сейфы (облачный не расшифровывается ключом
    локального) → вход облачным (введён пароль облачного сейфа — нужны облачные
    данные), старый локальный уходит в резервную копию `universe_vault_prev`;
  - открылись оба, одна линия (тот же мастер-ключ) → вход локальным, чтобы не
    терять свежие правки устройства;
  - открылся только локальный → вход локальным (обычный вход).
- `initAuth` показывает подсказку `#cloudHint2`, когда есть и локальный сейф,
  и облачный; тексты конфликта в `95-sync.js` переписаны под это поведение.

## 4. Хранилище (localStorage)

| Ключ | Что хранит |
|---|---|
| `universe` | главный объект: `{ version, events, notes, shopping, todos, photos, dates, wishlist, labels, backupDate }` |
| `universe_vault` | зашифрованный сейф: `{ ver:1, db (AES-GCM), keys: [{ who, k, s, iter, iv, a }] }` |
| `universe_user` | кто сейчас у сайта: `'gosha'` или `'dasha'` |
| `universe_theme` | тема: `'light'` или `'dark'` |

- **Версия схемы:** `DB_VERSION = 5` в объекте `db`. Загрузка через `migrateDB()`:
  добавляет новые поля старым данным (wishlist, backupDate, labels, version,
  `order` заметок) и конвертирует старые альбомы фото в лейблы. Правь `migrateDB`,
  когда меняешь форму данных, — и старые данные переживут апдейт.
- **Лимит** ~5 МБ (localStorage). Фото сжимаются до jpeg 900px / качество 0.82.
- Копия — вручную: **Настройки → Скачать копию** (JSON); при экспорте ставится `db.backupDate`,
  и Настройки показывают, сколько времени прошло с последней копии. Облака пока нет.

### Формы данных
```js
events:   { id, title, date:'YYYY-MM-DD', emoji, repeat: bool,
            endDate:'YYYY-MM-DD'|null (долгие события, repeat принудительно false),
            photos:[dataURL]|undefined (фото события; дублируются в db.photos с лейблом = title) }
dates:    { id, date, time:'HH:MM', from:'gosha'|'dasha'|'both'|undefined(legacy),
            responses:{gosha:null|'yes'|'no', dasha:null|'yes'|'no'},
            place, note, emoji, done: bool }
notes:    { id, text, ts, pinned: bool, author:'gosha'|'dasha'|undefined(legacy),
            order: num (drag&drop; старым назначается миграцией v5) }
shopping: { id, text, done: bool }   // todos — так же
wishlist: { id, text, link:'', data:dataURL|null,
            owner:'gosha'|'dasha', done: bool, ts }
            // старое поле type:'want'|'give' больше не используется (хранится, игнорируется)
photos:   { id, data: dataURL, title, labels: [строка], pinned: bool, ts, order: num }
labels:   [строка] — общий список лейблов (для кнопок-фильтров)
          // старое поле album:'строка' хранится у старых фото, игнорируется
```
- `START_DATE = '2026-03-30'` — старт счётчика «дней вместе» (функция `daysTogether()`).
- Порядок фото: `photoSort` — закреплённые сверху, дальше по `order` (по возрастанию).
  Новые фото получают `order:0`; drag&drop пересчитывает `order` всем фото списка.
- Легенда: `from` = кто приглашает. Свидания без `from` — «старые», отвечать могут оба.

## 5. Ключевые механики

### Вход, сейф и текущий пользователь
- Все данные — в **зашифрованном сейфе** `universe_vault`: общий AES-GCM ключ,
  обёрнутый (wrap) для каждого пароля (PBKDF2 → AES). Первый запуск мигрирует
  старый открытый `universe` в сейф и удаляет его.
- Разблокировка: `unlockWith(who, pass)`; смена/добавление пароля: `changePass` /
  `savePassFor`; замок `lock()` стирает ключ и данные из памяти.
- **Salt (PBKDF2) обязан храниться в wrap (`keys[].s`)** — был баг: без него после
  перезапуска сейф не открывался. AES-key при разблокировке **extractable** (`true`),
  иначе не сделать wrap для пароля партнёра.
- Текущий пользователь: `getUser()`/`setUser(u)`; чип в шапке `#userChip`.
- **Свидание/хотелка всегда от имени вошедшего** — селектов «кто» в модалках нет.

### Блок «Наша история» на главной (кольцо + коллаж + статистика)
- Обёртка `.hero-zone` вокруг `.hero-card` — без парящих фото (герой чистый).
- `renderProgressRing()` (в `src/35-memory.js`) рисует в `#progressRing`:
  `.history-main` = кольцо прогресса + `.ring-info` (годы/дни вместе) +
  `.history-photos` (коллаж), и `.history-stats` под ними.
- `historyPhotosHtml()` (в `src/30-home.js`): `HISTORY_PHOTO_SLOTS` — **3 слота**
  (разный размер 72–100px, повороты `rotate`, верхний сдвиг; без ровного ряда).
  Показываются `min(3, db.photos.length)` фото; `pickHistoryPhotos()` тасует
  копию `db.photos` ГПСЧ `mulberry32`, засеянным датой (`daySeed`) — коллаж
  **не перетасовывается** при каждом рендере в течение дня.
- **Приоритет — фото «в этот день»** (`onThisDayPhotos()` → `onThisDayItems()`,
  EXIF/дата события): они встают первыми в слоты, остальное — случайные.
  Когда такие есть — на коллаже бейдж `✨ В этот день` (`.hp-badge`).
- **«В этот день» без отдельного виджета:** события прошлых лет показываются
  чипами `.hs-otd-chip` в строке `.history-otd` прямо в блоке «Наша история»
  (строка появляется только когда такие события есть). Отдельный `#onThisDay`
  удалён — он дублировал коллаж.
- **Кнопка «🎲 Перемешать»** (`.hs-shuffle`, делегирование на `#progressRing`):
  `shuffleHistoryPhotos()` заново тасует случайную часть (фото «в этот день»
  остаются), результат фиксируется на день в `historyCollage = {day, sig, ids}`.
  `sig` — сигнатура состава галереи: при добавлении/удалении фото коллаж
  пересобирается (старый кэш не «залипает»).
- `photoSrc(p)` из кэша миниатюр; если кэш холодный — `<img data-photo-src>`,
  `renderHome()` дозаливает через `hydratePhotoImgs($('#progressRing'))`.
- Фото кликабельны: `data-photo` → глобальный обработчик открывает lightbox.
- Статистика `plural(n, one, few, many)` — чипы 📸 фото / 📅 событий / 💘 свиданий /
  📝 заметок. **Хотелки — чип с прогрессом**: `🎁 3/7` + мини-полоска `.hs-bar`
  (ширина = % исполненных из `db.wishlist`). Рядом — кнопка «🎲 Перемешать».
- Адаптив: ≤820px коллаж компактнее (70px), ≤480px — вниз на всю ширину (64px);
  бейдж на узких экранах переезжает вниз. Мобильная лента «Наши моменты»
  (`#mobilePhotosGrid`) удалена — фото на главной показывает только коллаж
  `#progressRing`, и на телефоне тоже.

### Свидания и ответы (важно!)
- Кнопка «💘 Назначить свидание» → модалка: дата, время, место, идея, эмодзи.
  «Дата» и «Во сколько» — в `.two-col .field` (label над полем, поля во всю
  ширину колонки — выровнены в одну линию).
  **Селекта «кто приглашает» нет** — свидание всегда от имени вошедшего
  (`from: getUser()` в `saveDateFromModal()`). Вариант «Вместе» не создаётся
  (старые свидания `from:'both'` рендерятся для совместимости).
- Пригласивший **уже согласен** — у него в статусе «💌 позвал/позвала», кнопок Да/Нет нет.
- Отвечает **только приглашённый**: `canAnswer = !from || from === 'both' || from !== who`.
- Если `from === 'both'` — отвечать могут оба.
- Ответ — переключатель: повторный клик снимает выбор (`resp[who] = val` → `null`).

### Прочее
- Календарь: события с `repeat` показываются каждый год; клик по дню → панель справа.
  События можно **редактировать** (кнопка ✏️ → `openEventModal(id)` с `editingEventId`).
- Главная: блок напоминаний «Скоро важное событие» **удалён** (дублировал таймер ⏳).
- Заметки: на карточке — **автор** (👦/👧, legacy без `author` → 💜 «Наши»),
  **✏️-правка** (кнопка `data-edit-note` или двойной клик → инлайн-текст с
  `data-save-note`/`data-cancel-note`), **drag&drop** (карточки `draggable`; на
  `drop` пересчитывается `order` всем заметкам). Сортировка: закреплённые сверху,
  дальше по `order`, в конце по времени. Закрепление/удаление — `togglePinNote()`/
  `deleteNote()` (может любой, без проверки автора). Добавление Ctrl+Enter.
- Списки: покупки 🛒 и дела ✅, счётчики «в работе».
- Фото: загрузка до 10 файлов за раз, лайтбокс, закрепление ⭐, **лейблы 🏷**:
  у фото несколько лейблов, фильтр сверху («Все фото» или один лейбл), выбор
  нескольких фото (кнопка ○ на карточке) и добавление лейбла сразу всем,
  удаление лейблов без вреда фото.
- Песня: «Ошибся номером» — **ТБКС**; `<audio>` грузит `music/nasha-pesnya.mp3`; если нет — подсказка.

### Витрина «📅 События» и удаление фото
- `renderEventBar()` вызывается из `renderPhotos()` (перед сеткой). Витрина видна,
  только когда `currentLabel === EVENT_LABEL`.
- Кнопки-уровни: `#eventYears` (годы, по убыванию), `#eventMonths` (месяцы
  выбранного года), `#eventTitles` (события выбранного месяца). Каждый уровень
  `display:none`, пока у него нет кнопок или не выбран родитель. На кнопках —
  счётчик фото: `eventPhotosCount(year, month, title)` считает уникальные фото из
  галереи, чьи события (`eventsForPhoto(data)`) подходят под фильтр.
- Один делегат клика на `document` обслуживает все уровни; повторный клик по
  активной кнопке сбрасывает этот уровень (и более глубокие); «✕ Сбросить»
  (`data-ev-reset`) сбрасывает весь `eventFilter`.
- `deletePhoto(id)`: удаляет из `db.photos` + вычищает dataURL из `ev.photos`
  всех событий (пустые массивы убирает) + `renderCalendar()` — удалённое фото не
  остаётся «мёртвой» миниатюрой в панели дня.

### Комплимент дня и таймер
- `renderCompliment()` — карточка под hero. Фраза выбирается **на весь день** по хэшу
  `toDateString()` (массив `COMPLIMENTS`, 20 штук) — при перезагрузке не прыгает.
- `renderCountdown()` — таймер до **ближайшего будущего** события/свидания
  (`nextTarget()` перебирает события и свидания, учитывая время свиданий).
  Тикает каждую секунду (`tickCountdown()` → `#countdownTick`). Если событий нет — скрыт.

### Тёмная тема
- Кнопка `#themeToggle` в шапке и `#settingsThemeBtn` в настройках → `toggleTheme()`.
- Значение в `localStorage['universe_theme']`, атрибут `data-theme` на `<html>`.
- В `styles.css` у `:root` базовые CSS-переменные; `[data-theme="dark"]` переопределяет
  палитру + точечные корректировки тёмных карточек.

### Хотелки (wishlist)
- Вкладка «Хотелки»; модалка `#wishOverlay`: **текст обязателен**, фото и ссылка — нет.
  **Селекта «для кого» нет** — хотелка всегда в список вошедшего (`owner: getUser()`
  в `saveWishFromModal()`).
- Вишлист **разделён по людям**: две секции «👦 Хотелки Гоши» и «👧 Хотелки Даши»
  (фильтр по `owner`, сортировка: невыполненные сверху). Секции «хочу подарить» нет —
  подарок это сюрприз, его не показываем в списке.
- `wishCard()` — карточка: фото (клик → лайтбокс через `data-photo`), ссылка (target=_blank),
  отметка «исполнено» ✅ (`data-wish-done`) и удаление.

### Конфетти
- `celebrate()` — 36 частиц 💜💖✨🎉🌸💞 падают через весь экран (класс `.confetti`).
- Срабатывает: (1) когда оба ответили «да» на свидание; (2) на главной, если сегодня
  событие (`rem.some(days===0)`) — **один раз в день** (флаг в sessionStorage).

### Настройки: бэкап и место
- `renderSettings()` — сколько занято в браузере (JSON размер) и сколько времени прошло
  с последней копии (`db.backupDate`). Если копии не было **30+ дней** — жёлтое
  предупреждение. Экспорт обновляет `backupDate`.

### Летающие сердечки
- `spawnHeart()` (💜💖💕🌸✨) теперь: раз в **3.8с**, **только на главной** и
  **пауза, пока открыта модалка** (`.overlay:not([hidden])`). Живут 12с.

## 9. 🚀 План релиза v1.0 (09.08.2026) — синхронизация + деплой

> **Критично:** без синхронизации сайт бесполезен для пары. Это главный приоритет.

### Фаза B: Облачная синхронизация (обязательно перед деплоем)

**Архитектура:**
```
┌─────────────────┐     HTTPS      ┌─────────────────┐
│  Гоша (браузер) │◄──────────────►│ Firebase RTDB   │
│  localStorage   │                │  vault_gosha    │
│  + IndexedDB    │                │  vault_dasha    │
└─────────────────┘                │  photos/{id}    │
                                   └─────────────────┘
┌─────────────────┐     HTTPS            ▲
│  Даша (браузер) │◄────────────────────┘
│  localStorage   │
│  + IndexedDB    │
└─────────────────┘
```

**Принцип:** localStorage — «правда» локально, Firebase — канал синхронизации.

### Решения перед фазой B (приняты 09.08.2026):

1. **Аутентификация:** **Anonymous Auth** (Firebase сам запоминает UID на устройстве).
   Оба устройства — «гости»; путь в RTDB — **общий `vaults/shared`**, правила
   `auth != null` (см. README). Данные на сервере — только шифртекст (zero-knowledge),
   поэтому открытый доступ не опасен. UID в localStorage не храним. Разделение
   «Гоша/Даша» остаётся внутри данных, как сейчас.
2. **Фото в облаке:** сначала **Base64-миниатюры (WebP ~256px) + метаданные в RTDB**
   (запись до 10 МБ не упирается), полные фото остаются **локально** в photoStore
   (IndexedDB) и в облако не летят. При росте объёма — миграция на Яндекс.Диск
   (10 ГБ), затем Cloudflare R2 (бэклог, фаза F).
3. **Два пользователя:** один общий anonymous UID (см. п.1), путь
   `vaults/<uid>` — общий зашифрованный сейф пары. Конфликты: **«последняя правка
   выигрывает»** по `syncTs`; CRDT — в бэклог.
4. **Безопасность:** в облако уходит **сам `universe_vault`** (зашифрован мастер-ключом,
   обёртки обоих паролей внутри) — никакого отдельного ключа не требуется; Firebase
   видит только шифртекст, прочитать без пароля нельзя.

**Статус:** модуль `src/95-sync.js` написан (push после save с debounce, pull при входе,
live-слушатель, конфликты по syncTs, offline-first, статус в настройках), хуки встроены,
тесты зелёные (375+60+16+10+16 ✓, в т.ч. `uni-sync.js` с моком Firebase: push/pull/
конфликт/мусор/live/stop и `uni-photo-sync.js`: загрузка всех 3 частей в Storage,
zero-knowledge, скачивание на втором устройстве, legacy-фото без оригиналов, чистка
удалений, сохранение типа файла). **B1 ✅** и **B3 ✅** выполнены: Firebase-проект создан,
config вставлен, RTDB rules опубликованы (README шаги 1–9); фото (оригиналы +
миниатюры) синхронизируются через Яндекс.Диск (`YANDEX_DISK_CONFIG.token`) и

живой двух-устройный тест — добавить/удалить фото на устройстве A и убедиться, что

### Фаза F: Миграция фото на Cloudflare R2 (когда Яндекс.Диск будет ~7–8 ГБ)

> ⚠️ Синхронизация фото уже сделана на **Яндекс.Диске** (B3 ✅, `photos/` +
> `db.photos` в сейфе). R2 остаётся как масштабирование, когда Диск упрётся
> в лимит 10 ГБ (или пропадёт доступ из-за OAuth).

**Триггер:** когда в Яндекс.Диске будет занято 7–8 ГБ (70–80% лимита).

**Что даёт:**
- 10 ГБ места (столько же, но без OAuth-зависимости от Яндекса)
- Безлимитный egress
- S3-совместимый API (можно использовать aws-sdk)

**План миграции:**
1. Создать R2 bucket в Cloudflare Dashboard
2. Написать Cloudflare Worker для signed URLs (бэкенд для авторизации)
3. Auth остаётся на Firebase (Anonymous Auth, тот же UID)
4. Написать скрипт миграции: скачать из Firebase → загрузить в R2
5. Обновить `src/95-sync.js`: фото теперь в R2, данные в Firebase
6. Протестировать на одном устройстве → раскатить

**Оценка времени:** 4–6 часов работы.

**Зависимости:** нужен Cloudflare аккаунт (бесплатно).

### Фаза G: P2P-синхронизация (экспериментально)

**Идея:** устройства синхронизируются напрямую через WebRTC, облако только для координации (signal server).

**Плюсы:**
- Нет лимитов облака
- Полная приватность (данные не покидают устройства)
- Работает офлайн (по локальной сети)

**Минусы:**
- Оба устройства должны быть онлайн одновременно
- Сложнее реализовать
- Конфликты сложнее решать

**Когда имеет смысл:** если облачные лимиты станут проблемой, а платить не хочется.

**Оценка времени:** 20–40 часов (сложная фича).

### Фаза H: Оптимизация фото

**Архивация старых фото:**
- Фото старше N лет → только миниатюры в облаке
- Оригиналы → локальный архив (внешний HDD / Google Drive)
- Экономит 90% места в облаке

**Сжатие при загрузке:**
- Качество 70–80% вместо оригинала
- WebP вместо JPEG
- Размер ~1–2 МБ вместо 5–10 МБ

**Lazy sync для фото:**
- ✅ Миниатюры и оригиналы синхронизируются сразу (B3, debounce 2.5с,
  полная сверка local ↔ Storage ↔ `db.photos`)
- ⏳ «Только по Wi-Fi / по требованию» — ещё не сделано

**Оценка времени:** 2–4 часа.

### Фаза I: Улучшения безопасности

**AES-ключ не-extractable:**
- Сейчас: ключ extractable (нужно для wrap пароля партнёра)

**Zero-knowledge для облака:**

- Даже если Firebase взломан — данные защищены
- Сейчас: данные уже зашифрованы мастер-паролем, это уже zero-knowledge

**Оценка времени:** 6–10 часов.
