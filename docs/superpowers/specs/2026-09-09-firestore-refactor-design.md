# Рефактор хранения: Firestore + ленивые фото

**Дата:** 09.09.2026
**Статус:** согласовано, готово к планированию реализации

## Зачем

Сегодня все данные пары лежат одним зашифрованным JSON-блобом сразу в трёх
местах: в localStorage браузера, в Firebase Realtime Database и (для фото)
отдельными зашифрованными файлами в Yandex Object Storage. Из этого следуют
три проблемы, ради которых затевается рефактор.

**Блоб — не база.** Нельзя запросить «события за август» или «последние 30
фото»: единственная доступная операция — скачать всё целиком и разобрать на
клиенте. Пагинация, поиск и любые выборки принципиально невозможны.

**Каждое устройство тянет всё.** Включая все фото во всех трёх версиях
(оригинал, показ-версия, миниатюра). При 500 фото это полтора гигабайта на
телефон по мобильной связи. Это главная жалоба и главный повод.

**Шифрование данных больше не защищает от того, от кого нужно.** После
перехода на Google-вход доступ к базе ограничен двумя аккаунтами на стороне
сервера. Клиентское шифрование текстов теперь защищает только от самого
провайдера — ценой невозможности всего перечисленного выше.

## Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| От кого защищаемся | От посторонних людей, не от провайдера | Доступ разграничивает база на своей стороне; «случайный залётный» не увидит ничего |
| База данных | **Firestore** | Та же консоль Firebase, вход и Cloud Functions не трогаются; запросы, пагинация, офлайн-кэш и живые обновления из коробки; бесплатный тариф без засыпания проекта |
| Supabase | Отклонён | Требует переноса аутентификации (заново Google OAuth), бесплатные проекты засыпают после 7 дней простоя, SQL-джойны в этой модели данных не нужны |
| Фото: хранилище | Остаётся Yandex Object Storage | Оплата рублями; бесплатный тариф Supabase/Firebase Storage не подходит по объёму и оплате |
| Фото: шифрование | **Сохраняется** | Не мешает ни скорости, ни ленивой загрузке (файл всё равно качается целиком на клиент); код уже есть; миграция фото не требуется |
| Тексты: шифрование | Убирается | Иначе невозможны запросы и пагинация — то есть весь смысл рефактора |
| Модель загрузки фото | Как iCloud Photos | Миниатюры всех фото локально (~12 МБ на 500 шт), показ-версии и оригиналы — по требованию |
| Интерфейс | Не переписывается | Костыли живут в слое данных; UI вылизан и покрыт 419 проверками |

## Архитектура

### Модель данных

Всё под одним поддеревом — одно правило доступа на всё, и модель остаётся
расширяемой без переписывания правил.

```
couples/main/
  events/{id}    title, emoji, date, endDate?, repeat, md, photos[], ts
  dates/{id}     date, time, place, idea, from, responses{gosha,dasha}, done, photos[], ts
  notes/{id}     text, author, pinned, order, ts
  lists/{id}     name, items[{id,text,done}], done, order, ts
  wishes/{id}    text, link, owner, done, photo?, ts
  labels/{id}    name, color
  photos/{id}    title, labels[], pinned, order, ts, shotAt?
  meta/settings  pushSubs{gosha,dasha}, photoKey
```

`photos/{id}` хранит **только метаданные**. Сами файлы остаются в Yandex по
путям `photos/thumb|full|orig/{id}`, как сейчас.

Подзадачи списков живут внутри документа списка, а не отдельной коллекцией:
их единицы, они всегда читаются вместе со списком, и так их порядок не
требует отдельной синхронизации.

**Повторяющиеся события** (годовщины) нельзя выбрать запросом по диапазону
дат, поэтому у события есть поле `md` формата `MM-DD`. Разовые события
тянутся запросом по диапазону `date`, повторяющиеся — запросом
`repeat == true` целиком (их единицы).

**Длительные события** (с `endDate`) создают отдельную ловушку: событие с 28
июля по 3 августа не попадёт в запрос «`date` в пределах августа», потому что
началось раньше. Поэтому запрос месяца всегда берётся с запасом назад — от
начала месяца минус 31 день, — а лишнее отсеивается на клиенте по `endDate`.
31 день — это максимальная длина события, которую поддерживает интерфейс;
если когда-нибудь появятся более длинные, запас нужно увеличить.

### Доступ

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function allowed() {
      return request.auth != null
        && request.auth.token.email in ['shakov.georgy@gmail.com', 'dashach98@gmail.com'];
    }
    match /couples/main/{document=**} {
      allow read, write: if allowed();
    }
  }
}
```

Всё, что вне `couples/main`, закрыто по умолчанию. Клиентский список
`ALLOWED_EMAILS` остаётся как удобство интерфейса, но границей безопасности
является это правило и такая же проверка внутри обеих Cloud Functions.

### Слой данных

Появляется модуль-репозиторий — единственное место, знающее про Firestore.
Интерфейс продолжает читать `db.events`, `db.notes` и прочее синхронно (179
обращений остаются нетронутыми), но смысл `db` меняется: это больше не «все
наши данные», а **кэш-проекция того, что нужно экрану**.

- `db.notes`, `db.lists`, `db.wishlist`, `db.labels` — целиком (их десятки).
- `db.events` — все повторяющиеся плюс загруженные месячные окна;
  `loadedMonths` помнит, какие месяцы уже в кэше.
- `db.dates` — от «месяц назад» и вперёд.
- `db.photos` — страницами по 60, курсор хранится в состоянии.

Запись заменяет 52 вызова `save()` на явные операции репозитория
(`addEvent`, `updateNote`, `removeWish` и т.п.). Каждая обновляет `db`,
перерисовывает нужный экран и пишет документ в Firestore. Оптимистичность
обеспечивает сам SDK: локальная запись применяется мгновенно, отправка идёт
фоном, офлайн-записи досылаются автоматически.

### Скорость

Ключевой механизм — встроенный офлайн-кэш Firestore
(`enablePersistence`). Повторные открытия отдают данные из IndexedDB
мгновенно, до обращения к сети; сеть догоняет фоном и молча обновляет.

- **Первый вход на устройстве:** один «горячий набор» — повторяющиеся
  события, события ±1 месяц, свидания за последний месяц и вперёд, все
  заметки/списки/хотелки/лейблы, `meta/settings`, первая страница фото.
  Десятки-сотни килобайт.
- **Повторные входы:** мгновенно из кэша.
- **Листание календаря:** соседние месяцы подгружаются фоном заранее.
- **Живые обновления:** `onSnapshot` на «горячих» коллекциях и на текущем
  окне событий — правки второго появляются сами.

### Фото

**Бакет закрывается полностью:** снимаются публичные `GetObject` и
`ListBucket`. Список фото теперь берётся из Firestore, а не листингом
бакета — это заодно убирает `listCloudPhotos()`.

**Cloud Function `photo-sign` расширяется:** к существующим `PUT`/`DELETE`
добавляется `GET`, и появляется пакетный режим — на вход список
`{id, part}`, на выход список подписанных ссылок. Клиент запрашивает
подписи пачкой на то, что сейчас нужно экрану, и держит их в памяти до
истечения срока.

**Политика хранения на устройстве:**

| Версия | Правило | Объём |
|---|---|---|
| `thumb` | скачиваются все, фоновой очередью, живут постоянно | ~12 МБ / 500 фото |
| `full` | по требованию, вытеснение по давности обращения | не более 150 файлов |
| `orig` | только по кнопке «скачать» | не кэшируется |

Лимит в 150 показ-версий — это порядка 50 МБ и заведомо больше, чем человек
пролистывает за один заход; при превышении вытесняется самая давно не
открывавшаяся.

**Показ:** при открытии фото сразу рисуется растянутая миниатюра, поверх неё
подставляется показ-версия по готовности; соседние фото предзагружаются,
чтобы листание шло без пауз. Существующий `photoStore` (IndexedDB) остаётся,
но меняет роль — из хранилища истины становится кэшем.

Расшифровка не меняется: файл скачивается, расшифровывается ключом из
`meta/settings.photoKey`, показывается из памяти.

## Миграция

Выполняется автоматически при первом запуске новой версии и идемпотентна:
если в Firestore уже есть данные — ничего не делает.

1. Взять расшифрованный `db` (ключ уже есть на устройстве или в `vaults/secret`).
2. Разложить по коллекциям батчами.
3. Скопировать ключ фото в `meta/settings.photoKey`.
4. Пометить миграцию выполненной.

**Старый блоб в RTDB не удаляется** — остаётся нетронутым, пока владелец
своими глазами не подтвердит, что всё на месте. Перед началом делается
обычный бэкап через «Скачать копию». Фото не мигрируют вовсе: они уже лежат
зашифрованными тем же ключом.

## Что удаляется

- `src/10-vault.js`: сейф, `save()`, PBKDF2, `tryUnwrapKey`, разовая миграция
  со старых паролей. Файл исчезает целиком — уцелевшие из него `unlockApp()`
  и `showAuth()` переезжают в гейт, где им и место. Криптографические
  примитивы (`aesEnc`/`aesDec`) живут в `00-core.js` и остаются: они нужны
  фото.
- Автозамок и связанная с ним кнопка «Скрыть» вместе с экраном
  «Открыть без входа» — при личных устройствах и входе по Google смысла нет.
- Блоб-синхронизация в `src/95-sync.js`: `pushVault`, `pullVault`,
  `writeVault`, `applyRemoteVault`, `listenRemote`, `forcePushVault`,
  разрешение конфликтов «сейф с другим паролем».
- `listCloudPhotos()` и полная выгрузка фото на устройство.
- Пути `vaults/shared` и `vaults/secret` в RTDB — после подтверждения.

Остаются: Google-гейт (упрощённый), Yandex-адаптер с подписанными ссылками,
`photoStore` в роли кэша, push-уведомления (подписки переезжают в
`meta/settings`).

## Чистка интерфейса

Отдельное требование: в интерфейсе не должно остаться кнопок, сообщений и
переключателей, обслуживающих механику, которой больше нет.

**Убирается:**

| Что | Почему |
|---|---|
| Кнопка «🔒 Скрыть (приватность на этом устройстве)» | Автозамка не будет: у каждого своё устройство и вход по Google |
| Кнопка «🔄 Синхронизировать сейчас» | Синхронизация становится автоматической — нажимать нечего |
| Строка статуса синхронизации | Норма не нуждается в отчёте о себе |
| Счётчики места в браузере (два) | После ленивой загрузки локально лежит кэш, а не «ваши данные» |
| Кнопка «🗑 Сбросить всё» | Данные стали общими и облачными: нажатие означало бы «стереть всё у обоих навсегда» |
| Кнопки «🔍 Диагностика облака» и «🔍 Диагностика уведомлений» с выводом | Обе отлаживали старую архитектуру; после рефактора будут врать |
| Жёлтые напоминания «копия давно не делалась» | Данные больше не живут только в браузере |
| Тосты: «Данные обновлены с другого устройства», «В облаке сейф с другим паролем», «В облаке есть фото с другим паролем», «Часть фото не синхронизировалась», «Не удалось сохранить» | Описывают ситуации, которых в новой архитектуре не существует |
| Экран «введи старый пароль», кнопка «Открыть без входа» и подсказка к ней | Уходят вместе с миграцией и автозамком |

**Появляется:** ненавязчивая плашка «нет сети» — единственный технический
индикатор, который остаётся. Она нужна, чтобы человек понимал, почему старое
фото сейчас не открывается.

**Остаётся без изменений:** «Скачать копию» и «Загрузить копию» (копия
бесполезна без восстановления, поэтому обе кнопки живут — просто молча, без
напоминаний), уведомления с их тумблером, тема, отключение анимаций, выход из
Google-аккаунта, экспорт календаря в `.ics`.

## Риски

**Потеря данных при миграции.** Снимается тем, что старый блоб не
удаляется, миграция идемпотентна, а перед стартом делается бэкап.

**Закрытие бакета ломает фото.** Поэтому это предпоследний шаг, после
того как подписанные ссылки проверены на живом сайте.

**Офлайн-персистенс Firestore в установленном на iOS приложении.** У
Safari есть особенности с IndexedDB в standalone-режиме; проверяется на
реальном устройстве до удаления старого кода.

**52 точки записи — легко пропустить одну.** Снимается тем, что `save()`
удаляется физически: любое забытое место перестанет собираться и всплывёт
в тестах, а не тихо потеряет данные.

**Расход чтений Firestore.** Живые подписки тратят чтения на каждое
изменение. Лимит бесплатного тарифа — 50 000 в день; для двоих
недостижим, но остаётся под наблюдением.
