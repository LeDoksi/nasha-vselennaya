# Ленивая загрузка фото (модель iCloud) — дизайн

> Реализует: канбан-карточка NV-7 («Ленивая загрузка фото по модели iCloud»).
> Статус: одобрено владельцем 2026-09-17, готово к переводу в implementation plan (writing-plans).

## Проблема

Сейчас (`src/95-photos-cloud.js`, `syncPhotos()`) при каждой разблокировке
приложение делает **полную сверку**: скачивает на устройство ВСЕ части
(`orig`+`full`+`thumb`) вообще всех фото обоих партнёров, которых там ещё
нет. С ростом галереи это означает всё больше трафика и всё дольше «прогрев»
при входе. Кроме того, бакет Yandex Object Storage сейчас публичен на
анонимное чтение (`GetObject`+`ListBucket` для `photos/*`, см. README раздел
B2) — «просто пора сделать правильно», раз запись уже закрыта подписанными
ссылками (`photo-sign`), а зависимость от публичного чтения — не более чем
исторический побочный эффект того, что закрыть запись раньше было
приоритетнее.

Владелец подтвердил: обе причины (трафик и открытый бакет) равнозначны,
цель — сделать архитектурно правильно, а не тушить конкретный пожар. UX-цена
принята: открытие ещё не скачанного фото в полном разрешении потребует сеть
и покажет короткую загрузку вместо мгновенного показа (как в iCloud Photos) —
миниатюры при этом остаются офлайн-доступными сразу.

## Текущая архитектура (для контекста)

- Чтение — анонимный GET/ListBucket напрямую в бакет.
- Запись — двухшаговая: короткий GET на Cloud Function `photo-sign`
  (`?method=PUT|DELETE&part=...&id=...`, заголовок `X-Firebase-Token`) отдаёт
  presigned-ссылку (SigV4, живёт 60 сек), клиент сам делает PUT/DELETE по ней
  напрямую в бакет.
- `syncPhotos()` — полная реконсиляция: `listCloudPhotos()` (анонимный
  ListObjectsV2 × 3 части) → сравнение с локальным `photoStore` и
  `db.photos`/`db.wishlist` → скачивание недостающего (`downloadCloudPhoto`,
  все 3 части сразу) и выгрузка недостающего (`uploadCloudPhoto`, все 3 части
  сразу), с ограничением параллелизма `SYNC_CONCURRENCY=4`.
- Светбокс (`src/85-lightbox.js`, `lbRender()`) уже показывает миниатюру из
  кэша мгновенно и асинхронно апгрейдит `img.src` через `photoUrl(p, false)`,
  а при зуме — через `photoOrigUrl(p)` (`upgradeLightboxToOrig`). Обе функции
  живут в `src/05-photostore.js` и сейчас читают **только** локальный
  `photoStore` — если блоба там нет, тихо возвращают `''`.

## Решение

### 1. Бакет + Cloud Function `photo-sign`

- Политика бакета: убрать правила «Разрешить всем `GetObject`/`ListBucket`»
  (README B2, шаг 4, правила 1–2). Остаются только служебное правило 3
  (доступ консоли) и запись, которая и так уже не анонимна.
- `photo-sign` (`functions/photo-sign/index.js`): `method` расширяется с
  `PUT|DELETE` до `PUT|DELETE|GET|LIST`.
  - `GET` — тот же `presign()`, что уже есть, без изменений внутри функции
    подписи; просто новое разрешённое значение метода.
  - `LIST` — presign на корень бакета (`objectPath = '/'`) с доп.
    query-параметрами `list-type=2&prefix=photos/<part>/&continuation-token=…`.
    `presign(method, objectPath, extraQuery)` обобщается: сейчас подписывает
    только фиксированный набор `X-Amz-*` query-параметров — extraQuery
    должен попасть в тот же canonical query string (отсортированный вместе с
    `X-Amz-*`), иначе подпись не сойдётся.
  - Новый batch-режим: `POST` с JSON-телом `{items: [{method, part, id}, …]}`
    (метод внутри item — `GET`, PUT/DELETE батчем не ходят, они и так
    одиночные немедленные действия), лимит **100 элементов** на запрос
    (защита от неограниченного тела). Ответ — `{results: [{id, part, url}, …]}`.
    Один и тот же `X-Firebase-Token` проверяется один раз на весь батч, не
    по элементу.
  - CORS: `Access-Control-Allow-Methods` дополняется `POST`;
    `Access-Control-Allow-Headers` уже включает `Content-Type` — без изменений.
  - Срок жизни ссылки: `EXPIRES_SECONDS=60` остаётся для PUT/DELETE
    (разовое немедленное действие). Для GET/LIST — новая константа
    `GET_EXPIRES_SECONDS=300` (пачка миниатюр может докачиваться дольше на
    слабой мобильной сети, а разница в риске утечки 60с vs 300с для
    зашифрованного контента несущественна).

### 2. Клиент — адаптер (`src/95-photos-cloud.js`)

- `makeCloudStorage()`: `getBlob()` и `listAll()` переходят с анонимного
  `s3Fetch` на подписанный запрос — `presignedFetch`, расширенный поддержкой
  GET без тела (сейчас принимает только PUT/DELETE с телом).
- Новая `batchPresign(items)`: один `POST` на `signFnUrl` вместо N
  одиночных GET-запросов на подпись; используется фоновой очередью миниатюр
  (см. ниже) для получения сразу пачки ссылок, после чего сами байты
  качаются параллельно (`mapLimit`, тот же `SYNC_CONCURRENCY`), как и сейчас.

### 3. Фоновая очередь — только миниатюры

- `syncPhotos()`: список частей для **скачивания** сужается до `['thumb']`
  (было `PHOTO_PARTS` = все три). Логика реконсиляции (мусор, гонка с другим
  устройством, `probeCloudKeys` для проверки чужого ключа) не меняется —
  меняется только то, какие части считаются «недостающими для скачивания».
- **Выгрузка** (`uploadCloudPhoto`) не меняется: свои новые фото уходят в
  облако всеми тремя частями сразу, как сейчас — у автора и так есть всё
  локально в момент добавления, лениво загружать нечего.
- `listCloudPhotos()` вызывается для каждой части отдельно, как сейчас —
  просто сам HTTP-запрос теперь идёт через подписанный LIST вместо
  анонимного.

### 4. Ленивая докачка full/orig — по требованию

- `src/05-photostore.js`: `photoUrl(p, useThumb)` и `photoOrigUrl(p)` — если
  `photoStore.getFull`/`getOrig` вернул пусто, вызывают новую
  `ensureCloudPart(id, part)` (в `95-photos-cloud.js`) **перед** повторной
  попыткой локального чтения. `ensureCloudPart`:
  1. Проверяет через `photoStore.getMeta(id)`, нет ли части уже локально
     (защита от двойной докачки при повторном вызове).
  2. Если `syncStorage`/`masterKey` не готовы — возвращает `false` без сети
     (совпадает с текущим поведением «показываем что есть»).
  3. Иначе — `photoRef(part, id).getBlob()` (уже подписанный GET), парсинг
     `{e, m}`/легаси `{i,d}` (та же логика, что в `downloadCloudPhoto`),
     `aesDec` не требуется на этом этапе (шифртекст сохраняется как есть,
     расшифровка — заботa `photoStore.getFull`/`getOrig` при чтении, как и
     сейчас для локальных блобов).
  4. `photoStore.putEncrypted(id, …)`, сохраняя уже имеющиеся локально части
     нетронутыми (тот же паттерн `exOrig`/`exFull`/`exThumb`, что в
     `downloadCloudPhoto`).
- Светбоксу (`src/85-lightbox.js`) ничего не нужно переделывать: он уже
  показывает миниатюру мгновенно (`photoSrc(p)`) и асинхронно апгрейдит
  `img.src`, когда промис `photoUrl`/`photoOrigUrl` резолвится — просто
  теперь этот промис при необходимости сходит в облако, а не всегда
  возвращает мгновенный локальный результат.

## Порядок выката (важно!)

Флип бакета на приватный — **ручное действие в консоли** Yandex Cloud, не
часть кода. Делать его нужно **только после** того, как новый `app.js`
реально долетел до обоих устройств — учитывая `sw.js` (офлайн PWA-кэш),
старая версия с анонимным чтением может прожить ещё некоторое время после
деплоя. Иначе окно, где старый клиент пытается анонимно читать закрытый
бакет, ломает синхронизацию у того, кто ещё не обновился.

Implementation plan должен закончиться шагом-чеклистом (не кодом): «убедиться,
что оба устройства открыли приложение и обновили service worker, только
потом менять политику бакета вручную в консоли» — с явной пометкой, что этот
шаг выполняет владелец руками, а не агент.

## Обработка ошибок

- Сбой presign/GET одной миниатюры в фоновой очереди — не должен ронять всю
  очередь (как и сейчас `mapLimit` продолжает остальные, `stats.failed`
  копится, `syncPhotos` планирует повтор через `reportRepoFailure`-подобный
  паттерн уведомления, см. существующий `notify(...)` на `stats.failed`).
- Сбой `ensureCloudPart` при открытии фото в светбоксе — не бросает
  исключение наружу (та же защита `try/catch` внутри, что и в
  `downloadCloudPhoto`); светбокс просто продолжает показывать миниатюру,
  `img.src` не апгрейдится. Отдельного тоста на разовый неуспех не нужно —
  фоновая очередь и повторное открытие фото естественно повторят попытку.
- Batch-запрос на подпись целиком падает (сеть/401) — очередь миниатюр
  откатывается к одиночным запросам? **Нет** — YAGNI: просто ошибка логируется
  и очередь повторится по общему таймеру `syncPhotos`, как любой другой сбой
  сверки сегодня.

## Тестирование

- `tests/photo-sign-auth.js`: новые сценарии на `method=GET`/`method=LIST`
  (presign без исключений, тот же email-гейт) и на batch-режим (`POST`,
  лимит 100 элементов). Batch обрабатывает элементы независимо: невалидный
  `part`/`id` в одном item превращается в `{id, part, error}` в его месте
  ответа, а не роняет весь запрос 400-й — остальные items всё равно получают
  свои `url` (тот же принцип устойчивости, что у `foreign`/`unknown` в
  `probeCloudKeys` — один плохой элемент не блокирует остальные).
- `tests/uni-photo-sync.js`: существующие моки `fetchMock` переводятся с
  анонимного GET/LIST на подписанный поток (presign-запрос → мок отдаёт URL →
  GET по нему); новый сценарий — «локально нет full, `photoUrl()` вызывает
  `ensureCloudPart`, получает блоб, кэширует».
- `tests/uni-dnd.js`/остальные существующие наборы — не затрагиваются
  (лейблы/списки/заметки не связаны с этой веткой).

## Вне рамок (сознательно)

- Приоритизация очереди миниатюр (какие фото качать первыми — видимые на
  экране vs все подряд) — сейчас порядок совпадает с порядком реконсиляции,
  как и раньше; настоящая viewport-приоритизация (IntersectionObserver) не
  входит в этот план, YAGNI, пока не станет реальной болью при большой
  галерее.
- Фоновая докачка `full`/`orig` «про запас» (офлайн-доступ ко всей галерее
  в полном качестве) — сознательно отклонено вопросом-ответом владельца:
  принята iCloud-модель, где open = сеть.
- Firestore-флаги вместо листинга бакета — рассмотрено и отклонено (см.
  обсуждение), листинг остаётся источником правды, просто через подписанную
  ссылку вместо анонимной.
